## Part 2 - Bugs Found and Fixed

### Bug 1: `simulate_tournament.py` mislabeled teams in already-decided
knockout matches (third-place slot ambiguity)

**Symptom:** the live `/predicted` bracket showed "France beats Germany" in
the Round of 16, when the real match was Paraguay vs France (France won
1-0). Similarly Netherlands was shown beating Canada in the R16, when the
real match was Canada vs Morocco (Morocco won). Caught while spot-checking
the tournament sim after the day's first real penalty shootout, not from an
error or warning - the job runs clean and just produces a self-consistent
but factually wrong bracket.

**Root cause:** 8 of the 16 Round of 32 slots are filled by "best
third-place team from groups X/Y/Z" - a fixed assignment the feed (and
FIFA) makes from a lookup table, not a free choice. `assign_thirds()` in
`simulate_tournament.py` is a generic constraint solver: it finds *a* valid
team-to-slot assignment satisfying each slot's allowed-groups list, not
necessarily *the* one actually used. Once a match is played,
`resolve_knockout.py` has already copied the real team names into
`fixtures` from the feed - but `simulate_tournament.py` was ignoring that
ground truth and re-deriving team identity from its own (sometimes
different) permutation. When the sim's guessed opponent happened to be the
actual winner's stand-in, results looked right by luck; when it wasn't
(Paraguay's entire path was invisible to the sim, replaced by Sweden), both
the bracket display and the Monte Carlo tally itself (title odds) were
silently wrong.

**Fix:** `pipeline/jobs/simulate_tournament.py` - added `load_real_slots()`,
which reads `(home_fifa_code, away_fifa_code)` straight from `fixtures` for
every knockout match with both teams already known. Both `simulate_once()`
(the 5000-trial Monte Carlo) and `build_predicted_bracket()` (the single
most-likely-path display) now use this ground truth for any match number
it covers, and only fall back to the model's own group-standings /
third-place-assignment logic for genuinely undecided future slots.

**Verification:** smoke-tested at 200 trials (deleted after inspection, per
the cleanup discipline from the 2026-07-05 report), confirmed match 74 now
shows Germany vs Paraguay (Paraguay wins, matching the real 3-4 penalty
shootout) and match 77 shows France vs Sweden (France wins 3-0, matching
reality) - both previously mislabeled. Re-ran the full 5000-trial simulation
to replace the live "latest" row; confirmed via raw HTML fetch of the live
`/predicted` page (bypassing a stale WebFetch-tool cache that briefly showed
the old bracket) that Paraguay now correctly appears losing to Germany's
opponent... i.e. beating Germany, then losing to France in the R16, exactly
matching the real bracket.

### Bug 2: `fetch_results.py` never read `score.et` (extra time)

**Symptom:** two Round of 32 matches decided in extra time - Belgium 3-2
Senegal and Argentina 3-2 Cape Verde - were recorded in `fixtures` as 2-2
and 1-1, the 90-minute score. This fed wrong data into three places: the
tournament sim (both matches looked like undecided draws with no pens data,
so the sim guessed a winner instead of using the real one - this was part
of what Bug 1's fix exposed and depended on being correct), the `/results`
page (showed the wrong final score), and `historical_matches` (the model's
rolling form/Elo trained on 2-2 and 1-1 instead of the real 3-2 wins for
five days).

**Root cause:** `fetch_results.py` only ever read `score.ft` (90-minute
score) and `score.p` (penalty shootout, only present if still level after
extra time). It never checked `score.et` (the score after the 30 extra
minutes, when a match went there) - so any match settled in extra time
without needing a shootout was silently recorded with the wrong,
lower-scoring result.

**Fix:** `pipeline/jobs/fetch_results.py` - final recorded score is now
`score.et` when present, otherwise `score.ft`. `score.p` is still recorded
separately as `home_pens`/`away_pens`, unchanged.

**Backfill:** `pipeline/jobs/backfill_extra_time.py` (new, one-off, kept for
the record per the `backfill_predictions.py` precedent) - re-reads the feed
and corrects any already-recorded fixture whose score doesn't match
`et`/`ft`/`p` as read today. Ran once: corrected `fixtures.home_goals` and
`away_goals` for match_num 82 (2-2 to 3-2) and 86 (1-1 to 3-2), backfilled
`home_pens`/`away_pens` for match_num 74, 75, 88 (three more pre-fix
shootouts that predate the 2026-07-05 fix and were sitting with NULL pens),
and propagated the same corrections into `historical_matches` (source
`openfootball-wc2026`) so the model's training data matches reality.

**What was NOT fixed, by design:** `predictions.brier_score` for match_num
82 and 86 was already filled in against the wrong (2-2 / 1-1) outcome before
this bug was found. The immutability trigger only permits `brier_score` to
move from NULL to a value exactly once - it explicitly refuses a second
write, which is the whole point of the guarantee. Per project rules this was
not touched or worked around. Quantified impact: match 82's stored Brier is
0.28671 (scored as a "draw" miss) vs what it would be against the true
home-win outcome, 0.12558 - the model actually favored Belgium (49.9%) and
they won, so this is unfairly penalized. Match 86's stored Brier is
0.46447 vs a true 0.02033 - the model gave Argentina 80.3% and they won by
extra time; this is the single most mispriced entry in the results log
purely due to the bug, not a modeling shortfall. Combined, the headline
Brier score would be about 0.0063 lower (0.1691 vs the current 0.1754) if
these two could be corrected. They can't, and that is the honest, permanent
state of the record - exactly the kind of thing the site's whole "immutable,
verifiable" pitch is built to surface rather than hide.

**Verification:** re-ran `fetch_results.py` after the code fix - clean, 0
errors, 0 new results (nothing new to fetch, as expected). Confirmed via raw
HTML of the live `/results` page that Belgium vs Senegal now shows the
correct final score 3-2 (previously would have shown 2-2). Re-ran
`verify_ready.py`, duplicate-team check, and missing-Brier check after all
changes - all clean.

Both fixes committed to main (pipeline job bugs with a clear root cause,
verified against the live feed and the live site, touching `fixtures` and
`historical_matches` only - never `predictions`).
