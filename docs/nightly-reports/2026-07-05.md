## Part 3 - Shootout Handling (backlog item 5)

**Problem:** `fetch_results.py` only ever read `score.ft` from the openfootball
feed. A knockout match level at full time is decided on penalties
(`score.p` in the feed), but nothing recorded that, so
`simulate_tournament.py`'s `load_actual_ko_winners()` couldn't derive a winner
from a tied FT score and kept sampling that match as open in the Monte Carlo
even after it was actually decided. Flagged as a known gap in CLAUDE.md and
called out as increasingly relevant in the last two reports since the
knockout rounds are now live. No real shootout has landed yet this tournament
(checked: all finished R32/R16 matches so far are decisive at FT), so this
was a pre-emptive fix ahead of the QF/SF rounds (Jul 10-15), not a reaction to
bad live data.

**Fix:**
- `db/migrations/007_shootout_pens.sql`: adds nullable `home_pens`/`away_pens`
  SMALLINT columns to `fixtures`. Verified no other query in the codebase does
  `SELECT *` against `fixtures` (checked pipeline, frontend, and schema.sql),
  so this is a pure additive change with no blast radius. Applied directly to
  the live DB and mirrored into `db/schema.sql`.
- `pipeline/jobs/fetch_results.py`: captures `score.p` alongside `score.ft` and
  writes it to the new columns whenever the feed provides it (only ever
  populated for a knockout draw).
- `pipeline/jobs/simulate_tournament.py`: `load_actual_ko_winners()` now falls
  back to `home_pens`/`away_pens` to pick a winner when `home_goals == away_goals`.
- `CLAUDE.md`: removed the now-fixed known gap, documented the new columns'
  purpose in the pipeline jobs section.

**Verification:**
- Confirmed the feed schema by pulling the 2022 worldcup.json (has real
  shootouts): `score.p` is `[home_pens, away_pens]`, present only when `ft` is
  level.
- Ran `fetch_results.py` after the migration - clean, 0 errors, 0 new results
  (as expected, nothing new to fetch).
- Ran `resolve_knockout.py` after the migration - clean, 0 errors, same output
  as before the change.
- Ran `simulate_tournament.py` with a reduced trial count as a smoke test -
  completed with no errors, correctly reported "Conditioning on 13 actual
  knockout result(s)."

**Self-caught issue:** the smoke-test sim run (300 trials, to keep the manual
check fast) inserted a real row into `tournament_sim`, which immediately
became "latest" and would have shown low-precision odds on the live
`/predicted` page and corrupted today's column in the champion-odds-over-time
chart (`getChampionHistory` picks the latest sim per day). Caught this before
finishing the review, deleted the contaminated row
(`DELETE FROM tournament_sim WHERE id = 39 AND n_sims = 300`), and confirmed
`verify_ready.py` and the live `/predicted` page were back to the legitimate
08:37 UTC / 5000-trial run. Lesson for future manual smoke tests of
`simulate_tournament.py`: it writes a real row on every invocation (no
idempotency, unlike `snapshot_odds.py`), so any ad hoc run against the live DB
needs an explicit cleanup step, or should be pointed at a scratch database
instead.

Committed to main (schema change is additive/non-breaking, verified against
every consumer of `fixtures`, and the fix directly closes a documented,
live-relevant gap).
